Synthèse des appréciations

Les notes se moyennent, pas les phrases. J'ai donc regroupé les trente appréciations par motif et compté combien de juges citent chacun comme facteur décisif.

30/30juges

La livraison décide la note, des deux côtés. Chaque juge, sans exception et sans voir les autres, a nommé le nœud terminal comme facteur décisif: le dashboard atteint-il quelqu'un, ou meurt-il dans les données d'exécution. Aucun autre critère n'a jamais été décisif. the grade turns on the terminal edge

11/30juges

Le dashboard livré par email reste une lecture étroite. Onze juges plafonnent volontairement leur note sous 90 pour cette raison, sur les deux outils. Aucun build des dix n'a produit une surface consultable et persistante. an emailed HTML body rather than a viewable surface

10/30juges

Un nœud terminal incapable de livrer, par nature. Sur les trois builds qui ne livrent pas, les juges pointent que le dernier nœud est un code ou un set, c'est-à-dire un type qui n'a aucune capacité d'envoi, pas un envoi mal configuré. no node type capable of presenting anything exists anywhere in the graph

4/30juges

Un nœud de fusion décoratif. Quatre juges relèvent un merge correctement câblé dont la sortie n'est jamais consommée: le compositeur va rechercher ses entrées par référence de nœud. Le câblage annonce une jointure qui n'a pas lieu. Observé sur les deux outils.

3/30juges

Un nœud qui ne fait pas ce que son nom dit. Trois juges signalent un nœud nommé pour trier qui ne fait que remettre en forme, le tri réel étant délégué au modèle en aval.

0/30juges

Aucun juge n'a reproché la décomposition multi-agent. Les dix builds obtiennent au moins 19 sur 25 sur l'idée et sur les liaisons. Trois agents pour les trois verbes de la demande, éventail depuis le déclencheur puis fusion: la forme est acquise chez les deux outils.

Le seul vrai défaut est aléatoire, et il touche les deux outils

Trois builds sur dix construisent le briefing HTML et ne le livrent nulle part. Deux viennent de n8n-as-code, un de Native MCP. Les sept autres finissent sur un envoi Gmail. Même outillage, même prompt, même modèle: c'est la variance entre tirages, pas une propriété.

C'est aussi pourquoi un run unique ne peut pas noter la qualité. Le run précédent, un build de chaque côté, avait donné 74 contre 87 sur exactement cet accident. Cinq builds par outil donnent 88 partout.

Ce que l'agrégat permet de dire, et ce qu'il ne permet pas

Solide: l'écart de tokens

Les deux distributions sont disjointes sur cinq builds chacune. n8n-as-code consomme moins, et ce n'est pas un tirage heureux. C'est le seul axe où l'écart tient sans réserve.

Fragile: l'écart de durée

Les étendues se recouvrent sur près de cent secondes. La médiane favorise Native MCP mais cinq builds ne suffisent pas à l'établir.

Nul: la qualité

88 des deux côtés. Les distributions de notes se superposent presque entièrement. Aucun des deux outils ne produit de meilleurs workflows que l'autre sur cette demande.

Inutilisable: la correctness

100 sur les dix artefacts. Elle contribue les mêmes 30 points aux deux composites. Elle vérifie que rien n'est cassé, ce qui n'arrive plus.

Composite pondéré: qualité 35, correctness 30, tokens 20, temps 15. L'écart final de 1,75 point provient entièrement des deux axes de coût, puisque qualité et correctness sont à égalité. Les juges ne voyaient qu'un workflow chacun, aveuglé, sans le nom de la branche, sans les scores de correctness et sans les coûts.
